# 設計書: 他大学の鳥人間サークルへの公開配布

本書は「このBotを他大学の鳥人間サークルでも導入できるようにする」ための方針を定める。
実装は本書の方針に沿ってフェーズ単位で行う。

## 要件（ユーザー確定）

0. **対象は他大学の鳥人間サークル**（人力飛行機・鳥人間コンテスト系）。
   「どんなサークルでも使える汎用運営bot」を目指すものではない
1. 招待URLを踏むだけで導入できる
2. 導入するサークルがVPSを持っていなくても使える
3. 導入するサークルが `.env` を編集しなくてよい
4. スプレッドシート相当のUIがある（データの保存先はスプレッドシートでなくてよい）

### 要件0の含意

対象ドメインを鳥人間サークルに限定するため、**ドメイン固有の語彙は資産であり、
除去対象ではない**。桁巻き・積層・主桁・機体進捗といった用語は他大学の鳥人間
サークルにそのまま通じるため、汎用語へのリネームはむしろ機能の意図を曖昧にする。

一方で、**サークルごとに異なるもの**（班構成、機体、桁の構成、チャンネル、ロール、
サークル名）はこれまで通りギルド別設定として扱う。「ドメインは固定、
組織構造は可変」が本プロジェクトの一貫した線引きとなる。

> **注**: この方針は `AGENTS.md` の「『鳥人間サークル専用』から『どんなサークルでも
> 使える汎用運営bot』への公開化作業を進めている」という記述と矛盾する。
> `AGENTS.md` 側を本書に合わせて更新済み。

## 1. 確定した方針

| 観点 | 決定 |
|---|---|
| 対象ドメイン | 他大学の鳥人間サークル（汎用化しない） |
| 配布モデル | 開発者が1インスタンスを常時運用し、各サークルは公開招待URLから招待するだけ |
| データUI | 自前Webダッシュボード（Discord OAuth2 ログイン + 表グリッド） |
| `/progress` の正本 | Google Sheets から PostgreSQL へ移行。Sheets は任意エクスポートに降格 |
| `/layer`（桁巻き積層記録） | 現状のまま維持（命名変更なし） |

### 1.1 配布モデル

要件1〜3を同時に満たす構成はこれ以外にない。導入者側にBotトークンもサーバーも
発生せず、`.env` は開発者（ホスト）が一度だけ設定する。

コード側はすでにこのモデルに対応済みである。

- 全テーブルが `guild_id` スコープのマルチテナント構成
- スラッシュコマンドはグローバル登録（新規サーバーで追加作業が不要）
- `on_guild_join` による自動セットアップ
- `/setup` でチャンネル・ロール・サークル名・班をDiscord上から設定
- `/todoist-setup` はModalからトークンを受け取り暗号化してDB保存
- 最小権限の招待URL生成（`bot.py` の `build_invite_url()`）

したがって残る作業は主に**運用面の切り替え**であり、大規模な改修ではない。

### 1.2 データUI

Discord OAuth2 でログインし、自分が所属するサーバーのデータだけを表グリッドで
閲覧・編集できるWebダッシュボードを自作する。

他案（NocoDB等のセルフホスト、Googleシートの自動作成）は、サークルごとに
フィルタビュー作成やメールアドレス入力といった**Discord外の手作業**が発生し、
要件1「招待URLを踏むだけ」を満たせないため採用しない。

リソース面の懸念は実測により否定された（本書 4章）。

### 1.3 `/progress` の正本移行

現状 `/progress` だけが中央Googleスプレッドシートを正本とし、ホスト側の
`GOOGLE_CREDENTIALS_PATH`（サービスアカウントJSON）に依存している。
このため導入サークルは自分のシートをサービスアカウントのメールアドレスに共有する
必要があり、これが要件3を崩している唯一の箇所である。

正本を他機能と同じ PostgreSQL に移し、Sheets 依存を解消する。

### 1.4 `/layer` の扱い

桁巻き・積層・桁という命名を維持したまま残す。要件0により対象は鳥人間サークルに
限定されるため、これらの用語は導入先にそのまま通じる。汎用語へのリネームは
機能の意図をかえって不明瞭にするため行わない。

`/progress`（機体→パーツ→部品の進捗ツリー）も同様に、鳥人間サークルにとって
中核的な機能として位置づける。

## 2. 各方針から導かれる作業

### 2.1 公開準備

- Discord Developer Portal で Public Bot を ON にする
- **`message_content` 特権インテントを削除する**（`bot.py` の `intents` 設定）。
  `on_message` ハンドラ・`message.content` 参照・prefixコマンドのいずれも
  存在せず、完全に未使用であることを確認済み。最小権限の原則として外す
- README を「各サークルが自分でBotを立てる」前提から
  「招待URLを踏むだけ」の手順に全面書き換え
- 利用規約・プライバシーポリシーの整備（公開Botの実務要件）

固有名詞のリネームは**行わない**（要件0）。README タイトル、`bot.py` の
presence 文字列「鳥人間サークル運営」、`EXEC_ROLE_NAME = "幹部"` はいずれも
そのまま維持する。

**Bot Verification について**: 100サーバーを超えると Verification と特権インテントの
審査が必要になるが、鳥人間コンテストに参加するサークルは全国で数十校規模のため、
この閾値に到達する可能性は低い。到達した場合は `members` インテント（班・メンバー
管理で実際に使用）の用途説明が必要になる。

**鍵管理**: 単一の `ENCRYPTION_KEY` が全テナントのTodoistトークンを保護する構成に
なるため、鍵の紛失は全サークルに波及する。バックアップとローテーション方針を
公開前に決めておく。

### 2.2 Webダッシュボード

#### プロセス構成: bot とは別プロセス

Botの常時接続が最重要資産であり、Web層のバグやメモリリークで
Discordから切断される事態を避ける。実測上のメモリ差は同一プロセス比で +26MB
にすぎず、隔離の価値がコストを上回る。

**ただし設定キャッシュの整合性に注意が必要**: Botは `config.for_guild()` の結果を
プロセス内にキャッシュしている。別プロセスのダッシュボードが `settings` を更新しても
Bot側は気づかない。PostgreSQL の `LISTEN/NOTIFY` でキャッシュ無効化を伝播させる
（asyncpg で数行で実装できる）。

#### 認証・認可

- Discord OAuth2（`identify` + `guilds` スコープ）
- `guilds` スコープのレスポンスに含まれる `permissions` から Manage Server 権限を判定
- 班長ロール等の細かい判定は既存の `utils/permissions.py` のレベル体系に合わせる
- セッションは署名付きクッキー（サーバー側セッションストアを持たない）

#### 最重要の設計制約: `guild_id` スコープの強制

ここを誤ると「他大学のデータが見える」という、本プロジェクトが最も避けるべき事故に
直結する。リポジトリ層はすでに `guild_id` を必須引数にしているため、
**Web層は「セッションで検証済みの `guild_id` 以外を絶対にリポジトリへ渡さない」**
という一点を守る設計にする。URLクエリやリクエストボディから来た `guild_id` を
そのまま信用しない。

#### その他

- 公開はHTTPS必須。リバースプロキシは Caddy（証明書自動取得）を推奨
- `utils/db.py` の asyncpg プールは `max_size=5`。ダッシュボードの同時読み取りと
  20分ごとの同期ジョブが競合しうるため、プールサイズを見直す
- フロントは表グリッドライブラリ（自己ホスト）で十分。SPAフレームワークは不要
- 対象テーブル: tasks / members / teams / schedules・schedule_votes /
  layer_records / progress

### 2.3 `/progress` のDB移行

- 機体→パーツ→部品の木構造を保持する `progress_nodes` テーブルを新設
  （`guild_id` スコープ、マイグレーション 009 として追加）
- 影響範囲: `services/progress_sheet_service.py` /
  `services/progress_sync_service.py` / `services/progress_tree.py` /
  `cogs/progress.py` と対応するテスト群
- 既存の中央シートからDBへの一回限りの移行スクリプトが必要

## 3. 実装フェーズ

| Phase | 内容 | 位置づけ |
|---|---|---|
| 0 | 公開準備（インテント削除・README書き換え・規約整備・Public Bot ON） | 低コストで即効。ここまでで Discord 上で完結する機能は公開可能 |
| 1 | `/progress` のDB移行 | Sheets依存の解消。クリーンな公開の前提 |
| 2 | Webダッシュボード（まず読み取り専用でリリースし、編集を後から追加） | 要件4の達成 |
| 3 | 依存削減（matplotlib / gspread の撤去） | Phase 1・2 の副産物 |

Phase 0 完了時点で公開自体は可能だが、`/progress` だけは Sheets 共有の手作業が
残る。公開を Phase 1 より先に行う場合は、新規サーバーでは `/progress` を
一時的に無効化する判断が必要。

## 4. リソース実測値

自前ダッシュボードの負荷懸念を検証するため、本リポジトリの venv で
常駐メモリ（Working Set）を実測した。

### 現在の bot プロセス

| 内訳 | 常駐メモリ |
|---|---|
| Python 素の状態 | 14.3 MB |
| + discord.py | +34.4 MB |
| + asyncpg / aiosqlite / cryptography | +3.5 MB |
| + matplotlib | +37.5 MB |
| + gspread / google-auth | +11.1 MB |
| **合計** | **約 101 MB** |

### ダッシュボード（FastAPI + uvicorn + セッション + HTTPクライアント）

| 内訳 | 常駐メモリ |
|---|---|
| Python 素の状態 | 14.2 MB |
| + fastapi / uvicorn / httpx | +33.8 MB |

### 結論

- 同一プロセス構成なら +34MB、別プロセス構成でも +60MB 程度
- **matplotlib 単体（37.5MB）のほうがダッシュボード一式より重い**
- Phase 1・2 の完了後、グラフ描画をブラウザ側に移して matplotlib を、
  エクスポートをダッシュボードのCSV出力に置き換えて gspread を撤去できる。
  その場合 bot は約 101MB → 約 52MB となり、
  **ダッシュボードを別プロセスで足しても総メモリは現状とほぼ変わらない**
- ディスクとCPUは論点にならない。Python依存が数十MB、フロントの静的ファイルが
  数百KB増えるだけで、DBのデータ量は変わらない（既存データを読むだけ）。
  サークル運営ツールの規模（同時接続はピークでも数十人）では負荷が発生しない

したがって、リソースを理由に自前ダッシュボードを避ける根拠はない。
実質的なコストはメモリではなく、**イベントループのブロッキング**（同一プロセス構成の
場合）、**接続プールの枯渇**、**公開HTTPSの攻撃面**の3点である。

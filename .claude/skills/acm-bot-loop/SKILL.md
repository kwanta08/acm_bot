# acm_bot ループコーディング

club-bot のコード変更は、**必ずこのループを回してから完了報告する**。
「実装したので確認してください」で止めるのは違反。全テストがパスして初めて完了。

## 0. 前提（毎回最初に確認）

- 作業ディレクトリは常に `club-bot/`（リポジトリルートではない）
- ルート直下 `AGENTS.md` は読んだ前提で動く。矛盾したら AGENTS.md が優先
- Python 実行系（Windows / venv あり）:
  - `club-bot\venv\Scripts\python.exe` があればそれを使う
  - なければ `python` / `python3`
- 依存が入っていなければ先に入れる:
  ```
  python -m pip install -r requirements.txt
  python -m pip install -r dashboard/requirements.txt   # 入れないと test_dashboard_*.py が skip される
  python -m pip install ruff pytest
  ```

## 1. ループ本体

各イテレーションは必ずこの順で進める。**途中でユーザーに戻らない**（§4 の停止条件を除く）。

### STEP 1: 受入基準を確定する（コードを書く前）
タスクを次の形に落として、1行ずつ書き出す。曖昧なら**最も素直な解釈で仮決めして明記**し、進める。

- 変更するファイル（推定）
- 完了条件（例: 「/progress で桁別の進捗が出る」「既存ギルドのDBが壊れない」）
- 検証方法（どのテストで担保するか。既存テストが無いなら**新規テストを書くこと自体をタスクに含める**）

### STEP 2: 最小の実装を書く
- 一度に触るのは 1 論点まで。無関係なリファクタを混ぜない（失敗の切り分けが不能になる）
- 新規データ・新規設定は必ず `guild_id` スコープ。グローバル状態を新設しない
- ギルド別設定は `config.for_guild(guild_id)` 経由で解決する
- スキーマを変えたら **同じイテレーション内で** `migrations/` か `utils/db.py` の `_migrate()` を書く（後回し禁止）
- サークルごとに異なるもの（班名・チャンネル・ロール・機体名・桁構成）をコードに埋め込まない。
  鳥人間ドメイン語（桁巻き・積層・主桁など）はそのまま書いてよい

### STEP 3: 検証する（この2つが緑になるまでが1周）
`club-bot/` で:
```
ruff check .
python -m pytest tests/ -q
```
- 高速に回したいイテレーション中盤は `python -m pytest tests/ -q -x --lf`（前回失敗分だけ・最初の失敗で停止）や
  `-k "progress or guild"` で絞ってよい。ただし**完了報告の直前は必ずフルセットを1回**通す
- `ruff check .` は CI と同じ設定（line-length 100 / py310）。`--fix` で直せるものは直してよいが、
  ロジックを変える自動修正は目視で確認する

### STEP 4: 失敗を解析して自分で直す
失敗を**分類してから**手を入れる。分類せずに当てずっぽうで直すのが一番時間を溶かす。

| 症状 | まず疑うこと |
|---|---|
| `AssertionError` で期待値が違う | 仕様の読み違い。テスト側が正しい前提で実装を直す。テストを都合よく書き換えない |
| `sqlite3.OperationalError: no such column` | マイグレーション漏れ（STEP 2 の migrations/_migrate） |
| Postgres 系テストが失敗 | DB 未起動。`docker-compose.yml` を確認。環境要因ならその旨を報告に明記 |
| `test_dashboard_*` が skip 祭り | `dashboard/requirements.txt` 未インストール（§0） |
| 別ギルドのテストが巻き添えで落ちる | グローバル状態を作った疑い。guild_id スコープに戻す |
| ruff の import 未使用・行長 | 機械的に修正。ロジックに触らない |

直したら STEP 3 に戻る。**これを全パスまで繰り返す。**

### STEP 5: 完了前チェック（全パス後に必ず）
- [ ] `ruff check .` と `python -m pytest tests/ -q` がフルセットで緑
- [ ] main ブランチに直接コミットしていない（作業は feature ブランチ）
- [ ] `.env` の実値・DISCORD_TOKEN・Todoist トークン・Google サービスアカウント JSON を触っていない（例は `.env.example` のみ）
- [ ] 新規データ／設定はすべて guild_id スコープ
- [ ] スキーマ変更にマイグレーションが伴っている
- [ ] Discord API 呼び出しは `discord.HTTPException` を捕捉している
- [ ] 実装とドキュメント（README.md / docs/）が矛盾していない（矛盾したら両方直す）
- [ ] コミットは**ユーザーから明示指示があったときだけ**（指示がなければコミットしない）

## 2. 完了報告の形

```
## 変更内容
- <ファイル>: <何を、なぜ>

## 検証
- ruff check . : パス
- pytest tests/ -q : NN passed, MM skipped（skip理由: ...）
- ループ回数: N周（主な失敗: ...→ ...で修正）

## 残課題 / 判断したこと
- <仮決めした解釈、次にやるべきこと>
```

## 3. 効率よく回すコツ

- **1周を小さく**: 実装30行 → 検証、が理想。200行書いてから回すと原因特定に周回を消費する
- **テストを先に書く**: 受入基準が曖昧なタスクほど、先に失敗するテストを書くとループが自動的に収束する
- **同じ失敗を2回見たら方針を変える**: 同じ箇所を同じ発想で3回直そうとしない
- **ログを足して1周使うのは有効**: 憶測で2周するより、`utils/logger.py` 経由で状態を出して1周する方が速い
- 長いタスクは feature ブランチを切り、論点ごとにコミット可能な状態を作っておく（コミット自体は指示待ち）

## 4. ループを止めてユーザーに聞くべき条件

以下だけは自走せず、状況・試したこと・選択肢を示して止まる。

- 同じテストが**3周直しても**緑にならない
- 受入基準そのものが矛盾している／どちらの仕様が正か決められない
- 既存ギルドのデータを壊す破壊的変更が避けられない
- 秘密情報や本番 DB に触る必要が出た
- テスト自体が間違っていると判断した（テスト書き換えは勝手にやらず、根拠を示して確認する）

## 5. 付属スクリプト

`scripts/loop_check.sh`（bash / Git Bash）と `scripts/loop_check.ps1`（PowerShell）は、
ruff と pytest をまとめて実行し、失敗だけを圧縮して出力する。ループ中はこれを叩くのが速い。

```
bash scripts/loop_check.sh            # フル
bash scripts/loop_check.sh --fast     # -x --lf で前回失敗分のみ
bash scripts/loop_check.sh -k progress
```
